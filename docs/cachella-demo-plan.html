Recommendation: build a presenter-operated CPU demo, available during explicitly opened sessions. Use a small corpus, one Machine and local storage. An assumed monthly envelope of $7.95 leaves $2.05 below the $10 boundary.

The original goal needs a scope change. Fly’s GPU service is deprecated. A leading large-model deployment with a high-throughput GPU engine and a validated LMCache savings benchmark is outside this plan. This version demonstrates private multimodal retrieval and small-model inference. [1]

1. Scope and feasibility

The product slice is the knowledge-search and grounded-answer experience of a Notion-style assistant: upload a file, find relevant evidence across formats, inspect the source, and ask a question. Rich document editing, team collaboration and a full workspace platform remain expansion work.

What the budget can demonstrate

Assumed operating scale: one workspace, one active inference job, up to three authenticated viewers, 100 source files, 500 MB of original media and 5,000 searchable chunks. This is an evaluation workload; none of these limits is a measured capacity result.

2. Budget and assumptions

Runtime allocation: reserve 10 hours for ingestion, 10 for evaluation and deployment checks, and 20 for demonstrations. Every model load, warm-up, idle period and failed job consumes this same 40-hour allowance. A full month at the conservative compute rate alone would be $57.60.

Use the existing Fly subdomain. Provision a single replica, one volume and no paid database, object-store extension, dedicated IP or monitoring service. Keep paid external model API usage at zero.

3. System architecture

Proposed stack: a small server-rendered interface, FastAPI, SQLite with FTS5, normalized vectors stored alongside chunk metadata, FFmpeg for media decoding, an embedding subprocess and a llama.cpp generation subprocess. Keep the runtime within one Fly Machine and serialize expensive work.

Separate model processes allow memory to be reclaimed after each stage. Keep the embedder resident during search sessions when measured memory permits. Unload it before generation if peak memory approaches the limit. Load weights from the volume so restarting avoids repeated downloads.

At 5,000 chunks, a 768-dimensional float32 vector matrix contains 15,360,000 bytes of raw vector data. Exact cosine search is a sensible initial implementation at this scale. Measure its latency before adding a separate vector service. Database, metadata and Python memory are additional.

Data model: workspaces, users, memberships, documents, document versions, chunks, jobs, query runs and usage counters. Each chunk records its workspace, source version, model revision, media type, content hash, page or time range, extracted text and embedding dimensions.

The full embedder’s raw float32 weights are approximately 2.96 GB by parameter-count arithmetic. Activations, decoding buffers, libraries and the application increase memory usage. The proposed 8 GB Machine is a starting hypothesis; a measured peak below 6.5 GB is the release gate.

For the embedder, start with 768-dimensional normalized vectors. Google supports dimensional truncation; evaluate 256 dimensions only after recording the baseline. Keep model versions and dimensions consistent between stored content and queries. [4]

Use a 4,096-token generation context, at most four concise evidence excerpts and a 192-token answer limit. Treat this model as an experimental answer composer. Retrieval and source inspection must remain useful when it abstains or times out.

Explicitly process the video soundtrack as audio. A frame-only route does not establish spoken-content retrieval. Keep media windows comfortably within the embedding model’s shared context limit. [4]

Transcripts and OCR: the first corpus includes source-provided transcripts and captions, with provenance labels. These support quotations and answers. Native media embeddings provide additional search evidence. Arbitrary live transcription, OCR and visual caption generation require separate CPU feasibility checks; missing text produces a source-only result.

Retrieval sequence: validate access → embed the query → retrieve top 20 semantic and top 20 keyword candidates within the authorized workspace → combine with reciprocal rank fusion → deduplicate overlapping segments → show the best eight sources → supply up to four text-bearing sources for generation. Skip an additional neural reranker in the first version.

Update discipline: hash original content, assign immutable versions, index into staging, then atomically activate the new version. Jobs checkpoint after each segment and resume after a stopped Machine restarts. Delete documents by removing active chunks, derived files and original media; enforce the retention policy on snapshots separately.

6. Demo experience

Use a synthetic product-launch workspace with 12 pages, 6 PDFs, 12 screenshots, 4 short audio recordings and 4 video clips. Include answers spanning several sources, conflicting versions and questions with no supporting evidence.

  1. Ask: “Why did we postpone the launch?” Search displays a planning page, a slide screenshot and a timestamped meeting segment.
  2. Inspect: selecting a citation opens the exact page or seeks the recording. Each result identifies how its searchable text was obtained.
  3. Answer: generate a short response from text-bearing sources, showing citations and an explicit insufficient-evidence response where needed.
  4. Repeat: rerun the same question with the application cache enabled and disabled, while keeping model output settings constant.
  5. Measure: display measured retrieval/generation timings and cache counters beside estimated infrastructure cost, with their evidence labels.

The interface needs four views: library and upload status, search and answer, source preview, and a presenter-only measurement panel. Text search is the initial query input; image and audio queries can follow after the core corpus retrieval tests pass.

Cache attribution: separately label embedding reuse, retrieval-result reuse and exact-answer reuse. An exact-answer hit avoids a generation request. This provides no evidence about LMCache KV-cache savings. Versioned keys must include workspace access scope, document versions, model revision and prompt configuration.

7. Fly operation and limits

Start with iad for the quoted cost basis. Assess the added latency for a Vietnam-based presenter. Moving to sin requires a new budget calculation. One Machine owns one mounted volume; there is no automatic replica failover.

Owner-controlled sessions: start the Machine through Fly before presenting; wait for health checks and model warm-up; stop it after the session. Disable request-triggered starts so web crawlers cannot wake paid compute. Fly documents this configuration’s availability tradeoff. [3]

# Illustrative configuration; validate before deployment.
primary_region = "iad"

[http_service]
  internal_port = 8080
  force_https = true
  auto_start_machines = false
  auto_stop_machines = "off"
  min_machines_running = 0

[[vm]]
  cpu_kind = "shared"
  cpus = 2
  memory = "8gb"

[[mounts]]
  source = "cachella_data"
  destination = "/data"

Pair this configuration with an application supervisor that ends the process after a maximum two-hour session, plus a Machine restart policy that leaves it stopped after exit. Verify the entire lifecycle with the actual Fly Machine configuration. HTTP autostop is disabled because indexing work may continue without active requests.

  • Runtime admission: reserve a session’s maximum runtime in SQLite before loading models. Refuse new work when the remaining allowance cannot cover it. Reconcile counters against actual Machine events.
  • Work limits: one inference job; queue depth five; per-stage timeouts; upload count, decoded size, media duration and response-byte quotas.
  • Budget stop: at 35 used hours, reserve the remainder for export and verification. Stop opening sessions when projected all-in spending reaches $8.00; retain headroom for billing lag and fixed charges.
  • Credentials: authenticated invitations, secure session cookies and secrets supplied through Fly. Keep Fly management credentials out of the web application.
  • Recovery: bounded snapshot retention and a tested SQLite backup/restore procedure. Use synthetic data until restore and permission checks pass.

These are application and operating controls. A supervisor failure, repeated manual starts or extra organization resources can still exceed the budget. Inspect usage before each demo and verify the stopped state afterward. Fly’s cost-management guidance is the operating reference. [7]

Report costs in two views: marginal compute per operation and allocated monthly cost per successful answer. The latter includes indexing, idle runtime, storage, snapshot and release costs. Record the number of successful answers and the covered billing window beside every unit-cost figure.

Valid savings experiment: use the same corpus and exact query set with cache disabled, then enabled; separately measure cold and warm runs. Report cache hit rate and avoided inference work. A lower request latency alone does not establish a lower monthly bill when the Machine remains running for the same session duration.

10. Failure paths and boundaries

  • Embedder too slow: retain pre-indexed content, reduce permitted live-ingestion work, and measure an optimized CPU runtime. If text-query latency still fails, mark the interactive demo blocked under this budget.
  • Memory exceeds the gate: release each model process between stages, reduce media resolution and batch size, and rerun the four-modality checks. Any larger Machine requires a smaller active-hour allowance.
  • Generation quality fails: ship search, evidence excerpts and source previews. Clearly mark generated Q&A incomplete.
  • New model integration fails: pin a working supported runtime after reproducing the issue. A text-only fallback must explicitly show reduced modality coverage.
  • Document contains malicious instructions: treat retrieved content as evidence data, disable agent actions and secrets access, and test prompt-injection cases.
  • Single host or volume unavailable: show service unavailability, recover from backup and reindex if required. This design offers no production availability guarantee.
  • Budget is exhausted: stop sessions and preserve stored data. Resume only after a new allowance is available or the scope is explicitly changed.

Deferred product scope: full Notion editor parity, synchronized enterprise connectors, arbitrary-hour recordings, automatic meeting transcription, real-time collaboration, production SSO, high concurrency and formal compliance certification.

Deferred infrastructure scope: large frontier-quality generation, production GPU inference, validated LMCache integration, multi-region availability and replicated storage. Revisit these when the hosting constraint or budget changes.

11. Decisions and open gates

Selected for this draft: all application inference on Fly CPU; one manually started Machine; EmbeddingGemma 2 as the first embedding candidate; a 4-bit sub-billion-parameter generator; SQLite; synthetic evidence; explicit monthly runtime limits.

Assumptions to confirm during implementation: presenter-operated availability is acceptable, the corpus is small, the $10 limit covers this project, and the chosen Fly region’s actual quote fits the envelope.

Required before deployment: model/runtime compatibility, CPU timing and memory evidence, account-specific billing calculation, watchdog and restart-policy verification, permission review, and a backup restore check.

Draft status: architecture and scope proposed; public documentation researched. Application implementation, model benchmarks, account inspection and deployment have not been performed. This document provisions no resources.
